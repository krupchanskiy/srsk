## Фаза 3. Логика и сценарии

### Роли
Суперпользователь, старший (`worship_approve`), пуджари (`worship_write`),
читатель (`worship_view`), человек без прав на модуль.
Для каждой: что видно в меню, какие кнопки есть, что отвечает база.

### Состояния данных
Пусто · один элемент · много (сто статей, сорок человек, год расписания) ·
архив · отменённое · истёкший срок волонтёра · человек в отъезде ·
правка на утверждении · конфликт версий.

### Сквозные сценарии
1. **Стандарт:** создание → черновик → отправка старшему → возврат автору →
   правка → отправка → правка старшим → утверждение → откат к прежней версии →
   вывод из действия → возврат из архива.
2. **Расписание:** назначение и снятие, второй человек в клетке, отмена дня,
   разовая служба, отметка «меня не будет», повтор недели на 1–4 недели,
   границы недели, переход через месяц и год.
3. **Люди:** добавление команды и волонтёра со сроком и бессрочно, смена вида,
   вывод из отдела и возврат, допуски к службам.
4. **Загрузка:** три периода × три состава, пустой отдел, один человек.
5. **Подборки:** сбор, порядок пунктов, выдача человеку и группе, отзыв.
6. **Галерея:** загрузка пачкой, обложка, закрытая папка, снимок в стандарт.
7. **Поиск:** слово, опечатка, тег, пусто, двести находок.
8. **Закладки:** постановка, снятие, удалённая статья в списке.

**Чиню сразу:** всё, что явно сломано или ведёт в тупик.
**Оставляю на твоё решение:** то, что меняет договорённости о работе отдела.

**Готово, когда:** каждый сценарий пройден на предпросмотре или на боевой базе
в транзакции с откатом; список расхождений в отчёте.

## Фаза 4. База и безопасность

1. `get_advisors` — security и performance, разбор каждого предупреждения.
2. **RLS:** под каждой ролью (через `set_config` + `set local role`,
   всё в транзакции с откатом) проверить чтение и запись по всем таблицам
   модуля. Отдельно — аноним: ключ `anon` публичен, через него не должно
   быть видно ничего из модуля.
3. **Функции:** идемпотентность повторного вызова, сравнения с NULL,
   права внутри (`worship_can_*`), поведение при отсутствии данных.
4. **Индексы:** `EXPLAIN` для тяжёлых запросов — поиск, расписание на неделю,
   загрузка за месяц, лента изменений. Добавить недостающие.
5. **Целостность:** осиротевшие строки, несогласованные статусы версий,
   назначения на отключённые службы.

**Готово, когда:** советники чисты или каждое предупреждение объяснено;
ни одна роль не видит и не меняет лишнего; тяжёлые запросы идут по индексам.

## Фаза 5. Скорость — главное направление

Сначала замер, потом правка, потом повторный замер. Каждая правка — с цифрами «было/стало».

### 5.1 Замер (Playwright + трассировка)
На каждой странице модуля, на «телефоне» с замедленной сетью (Fast 3G, CPU ×4):
- время до первой отрисовки и до готовности контента (FCP, LCP);
- блокировка основного потока (TBT) — сколько съедает компиляция Tailwind;
- число запросов и вес: скрипты, стили, шрифты, картинки, запросы к базе;
- водопад: какие запросы к базе идут **по очереди**, хотя могли бы параллельно.

### 5.2 Запросы к базе
- Последовательные `await`, которые можно собрать в `Promise.all`.
- `select('*')` и лишние колонки — тянуть только нужное.
- N+1: запрос в цикле по строкам.
- Повторы одного и того же запроса за загрузку страницы.
- Что стоит положить в `Cache.getOrLoad` (службы, разделы, люди отдела)
  и где кэш не сбрасывается после правки.
- Тяжёлые RPC: `worship_search` (подзапросы на каждую строку), загрузка
  за месяц. `EXPLAIN ANALYZE`, недостающие индексы.

### 5.3 Картинки — подозреваю главную потерю
- Подписанные ссылки на снимки (`createSignedUrls`, час жизни) создаются
  заново при каждом заходе → браузер не может их закэшировать и качает
  снимки снова. Проверить и, если так, кэшировать ссылки.
- Сетка галереи, вероятно, грузит **полноразмерные** снимки в плитки
  размером 150–200 px. Проверить; если да — уменьшенные копии через
  преобразование картинок Supabase.
- `loading="lazy"` и размеры у всех `<img>`, чтобы страница не прыгала.

### 5.4 Статика
- Tailwind CDN: компиляция стилей в браузере на каждой странице — замерить вклад.
- DaisyUI `full.min.css` — вся библиотека целиком.
- Шрифты: Noto Sans и Noto Sans Devanagari по четыре начертания —
  что реально используется.
- Скрипты без `defer` блокируют отрисовку.
- Версии `?v=` и кэш GitHub Pages.

**Сам меняю:** запросы, кэш, картинки, `defer`, лишние начертания шрифтов.
**Только замеряю и предлагаю:** предсборку Tailwind и DaisyUI вместо CDN —
это перестройка всего приложения, решение за тобой. Приложу цифры выигрыша.

**Готово, когда:** у каждой страницы модуля есть замер «было/стало»,
последовательные запросы распараллелены, лишние убраны, картинки в сетках
лёгкие.

## Фаза 6. Код

### Корректность
- Гонки: ответ на старый запрос перетирает свежий (поиск, переключение недели,
  быстрые щелчки). Где нет защиты «поколением» — добавить.
- Двойные слушатели: перерисовка навешивает обработчик ещё раз,
  и действие выполняется дважды.
- Забытые `await`, необработанные ошибки RPC (молчаливый «ничего не произошло»).
- Отказ RLS на `update` — ноль строк без ошибки: везде ли проверяется ответ.
- Даты: `DateUtils.parseDate` для DATE-колонок, `.slice(0,16)` для TIMESTAMPTZ.
- Экранирование пользовательского текста во всех шаблонах (`innerHTML`).
- Кириллические составные `data-` — только `getAttribute`.

### Переводы
- Ключи, которых нет в `translations`, и ключи без английского и хинди.

### Порядок
- Мёртвый код и неиспользуемые функции (например, `worship_reorder`) —
  **нахожу и показываю, не удаляю.**
- Повторяющиеся куски (выпадашка «ещё», переключатель, сворачиваемая группа),
  которые просятся в общий файл.
- Согласованность версий `?v=` у скриптов и стилей.

**Готово, когда:** перечень с пометками «исправлено» и «на твоё решение».

- агент Д — разбор скорости: водопады запросов, лишние колонки, кэш, картинки;
- агент В — axe-core по страницам соседних модулей;
- агент Г — проверка граничных данных расписания и загрузки.

**Правки делаю сам, по очереди.** Каждая проверяется в браузере и уходит
отдельным коммитом с объяснением причины.

**Скиллы:** impeccable для разбора экранов, frontend-design для вида,
новый скилл доступности для прогонов.
