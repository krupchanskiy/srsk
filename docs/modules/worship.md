# Модуль Worship (Поклонение)

## Обзор

Хранилище знаний пуджарского отдела: как делается служение, кто это утвердил
и что с тех пор изменилось. Отвечает на вопрос «а как правильно?» без того,
чтобы спрашивать старшего в 4:20 утра.

- **Цвет модуля**: `#9b2226` (тёмно-красный)
- **Layout.init**: `module: 'worship'`
- **ТЗ**: [docs/worship/tz_worship.md](../worship/tz_worship.md)
- **План разработки**: [docs/worship/plan.md](../worship/plan.md)

Этап 1 (стандарты) сделан. Расписание, библиотека, галерея, теги, поиск,
подборки и разбор записей собраний — этапы 2–4, их ещё нет.

## Права и роли

| Право | Кто | Что даёт |
|-------|-----|----------|
| `worship_view` | вся команда (роль `team_member`) | читать действующие стандарты |
| `worship_write` | роль `worship_pujari` | писать, править, отправлять на утверждение, закрывать замечания |
| `worship_approve` | роль `worship_senior` | утверждать, возвращать автору, архивировать, вести разделы |

Суперпользователь обходит проверки прав, но **не** получает уведомлений отдела:
получателями считаются только те, кому право выдано ролью или персонально
(`worship_holders`).

## Данные

```
worship_sections      разделы (kind: standard | library), порядок, активность
worship_articles      тема: раздел, заголовок, статус, порядок, чем заменена
worship_versions      текст по версиям: статус, номер, документ, простой текст
worship_remarks       замечания «здесь не так»
worship_notifications события для рассылки (уникальны по event_key)
worship_notification_log  что ушло и что ушло бы
worship_settings      рубильник рассылки и чат отдела
worship_bookmarks     закладки и недавно открытое
```

### Где истина про состояние

Это главное, что нужно понять до чтения кода:

- **статус статьи** — существует ли тема и действует ли она: `draft` → `published` → `archived`;
- **статус версии** — роль конкретного текста: `draft` → `submitted` → `published` → `superseded`.

Статья с правкой на утверждении **остаётся** `published`: пока старший не решил,
в храме служат по прежней редакции. Очередь «ждут решения» — это версии
со статусом `submitted`, а не статьи.

Ограничения базы, а не порядок записи: у статьи ровно одна действующая версия
(`worship_versions_one_published`) и ровно один незавершённый текст
(`worship_versions_one_open`), номера версий уникальны внутри статьи.

### Формат документа

Текст хранится структурой, а не HTML:

```json
{ "blocks": [
    { "type": "p",    "spans": [{"t": "Начало в "}, {"t": "4:30", "b": true}] },
    { "type": "h2",   "text": "Что приготовить" },
    { "type": "ul",   "items": [[{"t": "Гхи в лампаде"}]] },
    { "type": "note", "text": "Если лампада погасла — зажечь в стороне." },
    { "type": "img",  "path": "<uid>/<файл>.jpg", "caption": "Алтарь утром" }
] }
```

Отрисовка собирает узлы через `createElement` + `textContent`, поэтому выполнить
чужой скрипт невозможно по построению, а не по бдительности. Единственная строка,
которую браузер всё же разбирает, — адрес ссылки, и он проходит белый список схем
(`WorshipDoc.адрес`). Чистить HTML в браузере было бы бессмысленно: публичный ключ
позволяет записать в базу что угодно напрямую.

Снимки лежат в приватном бакете `worship`, в документе — только путь; ссылки
выдаются на час (`WorshipDoc.ссылкиНаСнимки`).

## Функции

Статусы, номера версий и факт утверждения ставят только функции — политик записи
у `worship_articles` и `worship_versions` нет вовсе.

| Функция | Что делает |
|---------|-----------|
| `worship_save_draft(jsonb)` | создаёт статью и/или перезаписывает черновик; проверяет параллельную правку по `base_updated_at` + `base_known` |
| `worship_submit(uuid)` | отправляет на утверждение, пишет событие старшим |
| `worship_withdraw(uuid)` | отзывает правку обратно в черновик |
| `worship_approve(uuid)` | утверждает: берёт строку `FOR UPDATE`, присваивает номер, вытесняет прежнюю версию; повтор идемпотентен |
| `worship_approve_many(uuid[])` | то же пакетом, построчный отчёт, ошибка одной статьи не роняет остальные |
| `worship_return(uuid, text)` | возвращает автору с причиной |
| `worship_archive(uuid, text, uuid)` | отменяет стандарт, запоминает причину и чем заменён |
| `worship_unarchive(uuid)` | возвращает из архива |
| `worship_restore_version(uuid)` | копирует прежнюю версию в черновик |
| `worship_delete_draft(uuid)` | удаляет черновик статьи, которая никогда не действовала |
| `worship_reorder(uuid, int)` | двигает статью в разделе на одну позицию |
| `worship_remark_add/close` | замечания |
| `worship_touch_recent(uuid)` | отмечает «открыл», подрезает список до семи |
| `worship_notify_pack(dry, log)` | служебная: собирает события в письма, группируя |
| `worship_notify_stale()` | служебная: напоминает о висящих дольше месяца |

После каждой функции идёт `revoke … from public, anon, authenticated` и явный
`grant` роли `authenticated`: Supabase выдаёт EXECUTE по умолчанию, и отзыв
у `public` с `anon` этого не снимает.

## Уведомления

События пишутся внутри функций, а не из браузера: двойной клик дал бы два
сообщения, закрытая вкладка — ни одного, а любой вошедший смог бы написать
в чат отдела от имени системы. `event_key` делает повтор безвредным.

Отправщик группирует: три утверждения подряд — одно сообщение в чат отдела,
возврат и замечание одному человеку — одно письмо. Доставка идёт через
`tg_outbox` (личный адрес — `vaishnavas.telegram_chat_id`, общий — настройка
`department_chat_id`).

**Рассылка выключена рубильником** `worship_settings.notify_enabled = false`:
пока он выключен, всё уходит только в журнал. Чтобы включить после того, как
появится чат отдела:

```sql
update worship_settings set value = '<chat_id>' where key = 'department_chat_id';
update worship_settings set value = 'true'      where key = 'notify_enabled';
```

Расписание уже заведено: `worship-notify` каждые полчаса, `worship-stale-monthly`
первого числа.
