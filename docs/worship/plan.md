# Поклонение — план разработки

Составлен 18.10.2026 по [ТЗ v2.2](tz_worship.md). Порядок работ, блоки, чем
проверяется каждый кусок.

## Как работаем

**Среда одна — боевая.** Отдельной базы для разработки нет, поэтому:

- проверки сценариев идут в транзакции с откатом, одним вызовом
  (`begin; … rollback;` — иначе MCP коммитит каждый запрос отдельно);
- проверка прав — симуляцией роли: подстановка `request.jwt.claims` **и**
  `set local role authenticated`, иначе правила доступа не применяются вовсе;
- каждая миграция сохраняется файлом в `supabase/migrations/` сразу после
  применения, с хешем, сверенным с журналом базы. На магазине я один раз
  отложил это «на потом» и восстанавливал текст из журнала.

**Деплой — обычный:** коммит в main, GitHub Pages собирает за пару минут.
Версии скриптов (`?v=N`) бампятся в том же коммите, иначе браузеры держат старое.

**Порядок внутри каждого блока всегда один:** данные → ограничения → правила
доступа → функции → проверка на откате → экран → проверка в браузере.
Экран, написанный раньше функций, всегда приводит к тому, что проверки
переезжают в браузер и там остаются.

# Этап 1. Основа: стандарты

Цель: отдел может переносить в систему то, что копилось годами. Ничего внешнего
не нужно — ни ключей, ни чата, ни новых учётных записей.

## Блок 1.1. Модуль, права, роли

- Запись модуля `worship`, цвет, пункт меню, `color-init.js`.
- Права `worship_view`, `worship_write`, `worship_approve`.
- Роли «Пуджари» (view + write) и «Старший пуджари» (все три).
- `worship_view` выдаётся ролям персонала **поимённо**.

**Проверка, без которой блок не закрыт:** под гостевой учётной записью право
не появляется. В базе 626 гостевых учёток против 22 сотрудников — если
`worship_view` просочится в гостевую роль, стандарты прочтёт любой, кто
когда-либо регистрировался на ретрит.

Размер: маленький. Зависимостей нет.

## Блок 1.2. Данные стандартов

Таблицы `worship_sections`, `worship_articles`, `worship_versions`.

Ограничения, которые ставим сразу, а не потом:

- номер версии уникален в пределах статьи;
- действующая версия у статьи ровно одна (частичный уникальный индекс);
- у вида «материал» допустимы только состояния «действует» и «архив».

Правила доступа: чтение действующего — по `worship_view`; черновики, причины
возврата и архив — по `worship_write`; **политик записи нет вовсе**.

**Проверка:** из-под роли пуджари попытаться вставить версию напрямую и получить
отказ; из-под сотрудника не увидеть черновик.

Размер: средний.

## Блок 1.3. Функции жизненного цикла

`worship_save_draft`, `submit`, `withdraw`, `approve`, `return`, `archive`,
`restore_version`.

Внутри каждой — проверка права, проверка текущего статуса, проверка авторства
там, где нужно. В `approve`: блокировка строки, перепроверка статуса под
блокировкой, идемпотентность (повторный вызов возвращает «уже утверждено,
версия N», а не вторую версию и второе уведомление).

`save_draft` принимает отметку времени, с которой начинали править, и при
расхождении возвращает отказ вместе с чужой версией.

После каждой функции — отзыв права исполнения у публичной и анонимной роли
с выдачей роли вошедших. Supabase выдаёт это право по умолчанию, и «отозвать
у public и anon» его не снимает: на магазине это стоило отдельной миграции.

**Проверка на откате:** полный цикл (черновик → отправка → возврат → правка →
отправка → утверждение → правка → архив); двойное утверждение подряд; утверждение
чужого черновика пуджари без права; удаление черновика у статьи, которая уже
действовала.

Размер: большой. Это сердце этапа.

## Блок 1.4. Чтение

Экраны `standards.html` (разделы, плоский список, фильтры) и `article.html`
(текст, оглавление по заголовкам, история, печать).

Сравнение версий — по простому тексту, библиотекой с CDN, одной кнопкой
«что изменилось в этой правке».

Печать — только действующей версии, через `@media print`; в проекте есть
десяток образцов.

**Проверка:** в браузере, на телефоне тоже — оглавление и память прокрутки
это главный ежедневный сценарий.

Размер: средний.

## Блок 1.5. Редактор

Экран `edit.html`. Документ хранится структурно (формат редактора), HTML
не хранится. Фото из текста уходят в приватный бакет модуля, в документе —
ссылки.

Автосохранение пишет в память браузера. В базу — только по кнопке: иначе
автосейв начнёт воевать с проверкой параллельной правки.

Поле «что изменилось» обязательно, кроме первой версии.

**Проверка:** двое правят один черновик из двух окон; вставка картинки;
цикл «сохранил → открыл → сохранил» не меняет документ сам по себе.

Размер: большой. Самый неприятный кусок этапа — редактор всегда дороже, чем кажется.

## Блок 1.6. Очередь, замечания, уведомления

- Очередь «ждут решения» у старшего, с пакетным утверждением.
- `worship_remarks` — «сообщить о неточности», список рядом с очередью.
- `worship_notifications` + отправщик: события пишутся функциями, отправляет
  служебный процесс, **группируя** (несколько утверждений подряд — одно сообщение).

**Проверка:** сухой прогон отправки без реальной рассылки; двойной клик
по «Утвердить» даёт одно сообщение.

Размер: средний. Чат отдела понадобится только для боевой проверки — до тех пор
отправка работает «вхолостую» в журнал.

## Блок 1.7. Главная и первое наполнение

- `index.html`: блоки для трёх ролей.
- Первая версия без вопроса «что изменилось».
- Закладки и недавно открытое.

**Проверка этапа целиком:** перенести руками три-четыре настоящих стандарта
от начала до конца, глазами отдела.

Размер: средний.

3. Завести чат отдела в телеграме и включить рассылку рубильником

Уроки этапа, чтобы не наступать дважды:

- **Запрос supabase-js без `await` или `.then()` не уходит на сервер вовсе.**
  Ленивый билдер молча ничего не делает. Нашлось на «недавно открытом».
- **Отметку времени для проверки параллельной правки нельзя считать
  необязательной.** Тот, кто открыл действующий текст, черновика не видит —
  и затирал чужой, заведённый в это же время.
- **Агрегат по пустой выборке возвращает строку с NULL внутри**, а `format()`
  превращает её в текст: в письме появлялась строка «Дольше месяца ждут
  решения: .».
- **Перестановка по `sort_order` требует сначала раздать номера**: пока у всех
  ноль, поиск соседа по паре (номер, заголовок) находит не соседа.
- **Состояние статьи и состояние текста — разные вещи.** Первая схема делала
  «на утверждении» статусом статьи, и отправка правки убирала действующий
  стандарт из храма.

# Этап 2. Расписание

Нужен вход и подключённый бот постоянным пуджари — иначе половина отдела
не увидит своих служб. Это единственная внешняя зависимость этапа.

## Блок 2.1. Данные и люди

`worship_services`, `worship_people`, `worship_person_services`,
`worship_person_notes`, `worship_absences`, `worship_duties`,
`worship_day_overrides`.

Заметки о людях — **отдельная таблица с самого начала**: защита в Postgres
строчная, и поле в карточке уехало бы к любому, кто запросил список людей.

Ограничения: даты отсутствия проверяются, пересечения у одного человека
запрещены; назначение уникально по службе, дате, человеку и роли.

## Блок 2.2. Функции назначения

`duty_set`, `duty_clear`, `week_copy` (идемпотентная), `absence_set`
(человек ставит себе сам), `absence_clear`.

Недоступность — жёсткая проверка внутри функции. Занятость в то же время,
отсутствие допуска и перегруз — **предупреждения интерфейса, не ограничения базы**:
иначе сломается заявленный сценарий «старший вправе поставить кого угодно».

## Блок 2.3. Шахматка и день

Неделя на компьютере, день на телефоне, карточка человека, вкладка людей.
Состояния клетки рисуются до вёрстки: недоступен, не отмечен, занят,
разовая служба, отменённая, двое в клетке — и сочетания.

Назначение кликом. Перетаскивания нет: в проекте его нет нигде, и начинать
с него в матрице — плохая идея.

## Блок 2.4. Напоминания и гостевой вид

- Вечернее напоминание текстом (не ссылкой), сводка на завтра в чат отдела.
- Накопление правок расписания в одно сообщение.
- Функция для портала: службы и времена на день, без имён.

**Проверка:** сутки в сухом режиме, с записью того, что ушло бы.

# Этап 3. Библиотека, галерея, теги, поиск, подборки

## Блок 3.1. Хранилище и общий код

- Приватный бакет модуля, ссылки ограниченного срока.
- Поднять общий предел размера файла в проекте (он один на весь проект).
- Вынести `photos/js/upload.js` и один из трёх просмотрщиков в общий модуль.

Это первый блок этапа нарочно: на нём стоит и библиотека, и галерея.

## Блок 3.2. Библиотека и галерея

Карточки материалов, наборы снимков, уменьшение с учётом поворота из файла,
закрытые наборы, дата события.

## Блок 3.3. Теги и поиск

Словарь с нормализованным ключом, связь двумя полями, слияние функцией.
Поисковый образ в версии, собирается триггером; поиск по похожести
(расширение `pg_trgm` — установить). Выдача группами.

## Блок 3.4. Подборки

Составление, выдача человеку или ретриту, печать.

**Выдача в портал гостя — отдельный кусок в другом приложении:** там своя
авторизация и свой слой данных. Оценивается и делается после того, как
подборки работают внутри модуля.

Библиотека, галерея, теги, поиск и подборки сделаны и лежат в main
(миграции 221–233, экраны `library`, `material`, `gallery`, `album`,
`search`, `kits`, `kit`, общий модуль снимков `js/media.js`).

Этап 2 (расписание) пропущен сознательно: он держится на входе
и подключённом боте у постоянных пуджари, а этого пока нет.

Уроки этапа:

- **Прямой `update` по таблице без политик записи проходит без ошибки
  и не меняет ни строки.** Карточка материала «сохранялась», а описание
  не записывалось. Если у таблицы политик записи нет — всё идёт через функцию.
- **Обычная похожесть `similarity` для поиска не годится**: она сравнивает
  строки целиком, и короткий запрос в длинном тексте тонет. Нужна
  `word_similarity` — похожесть запроса с отдельным словом.
- **`Layout.pluralize` принимает формы по языкам**, а не массив, и само
  подставляет число. Переданный массив роняет страницу целиком.
- **Поворот снимка нужно читать из файла.** Камера пишет кадр как есть
  и помечает, где верх; без этого половина снимков с телефона ложится набок.

# Этап 4. Разбор собраний

**Начинается не с экранов, а с прототипа пути файла.** Загрузка в приватный
бакет → ссылка ограниченного срока → Deepgram → ответ по готовности → разбор
в OpenRouter → запись результата. Одна настоящая запись собрания, никакого
интерфейса.

Пока этот путь не пройден от начала до конца, экраны `meetings.html`
не верстаются: риск здесь не в ИИ, а в стыках.

Дальше: статусы и повторные попытки, отложенное удаление аудио по расписанию,
карточки решений с правкой текста и сохранением машинной формулировки.

Нужны оба ключа: Deepgram и OpenRouter.

# Чем заканчивается каждый этап

| Этап | Отдел может |
|------|-------------|
| 1 | вести стандарты: писать, утверждать, читать с телефона, печатать |
| 2 | вести расписание, видеть свои службы, получать напоминания |
| 3 | хранить материалы и фотографии, искать по всему, выдавать подборки |
| 4 | превращать записи собраний в черновики стандартов |

Останавливаться можно после любого: каждый оставляет работающую систему.

# Что проверяем отдельно после этапов 1–3

Короткий прогон периметра, как делали в магазине:

- ни одно право модуля не попало в гостевую роль;
- прямая запись в закрытые таблицы отклоняется из-под каждой роли;
- черновики, расшифровки, заметки о людях и закрытые наборы не отдаются
  тем, кому не должны, **в ответе сервера**, а не только на экране;
- файл закрытого набора не открывается по прямой ссылке;
- повторные вызовы функций не плодят версии, назначения и сообщения.

# Риски, которые вижу заранее

**Редактор.** Самый вероятный источник переделок. Библиотеки без сборки
наперечёт, у каждой свои углы: вставка картинок, собственный формат документа,
потеря разметки при цикле сохранений. Если на нём застрянем — есть запасной
путь: простое поле с абзацами и заголовками без визуального редактора,
этого хватит для первых стандартов.

**Поиск.** Морфология на штатном словаре работает хуже, чем ожидают люди
(«одеть» не находит «одевание» — проверено). Поиск по похожести это чинит,
но требует расширения в базе; если его не поставить, придётся честно сказать
отделу, что поиск ищет по словам, а не по смыслу.

**Портал гостя.** Отдельное приложение, в котором я ещё не работал в этой
сессии. Выдача подборок и гостевой вид расписания живут там, и обе оценки —
предварительные.

**Люди без учётных записей.** Не технический риск, а организационный: пока
у Ачинтьи нет входа, а у волонтёров нет бота, расписание остаётся наполовину
бумажным. Сводка в чат отдела это смягчает, но не заменяет.
